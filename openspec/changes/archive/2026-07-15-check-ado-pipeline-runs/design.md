## Goals / Non-Goals

**Goals:**

- Add `adomi ado pipeline list` to traverse the Build API continuation sequence and return the valid `inProgress` runs received for the configured project, whether they come from YAML or classic Build pipelines.
- Add `adomi ado pipeline get <run-id>` to return one run's current overall status and terminal result when available.
- Return one stable compact JSON value with pipeline identity, run number, source revision, timestamps, and web link, using JSON `null` for unavailable result/timestamp/link values.
- Reuse existing profile, PAT, proxy, project, API-version, redirect, error-stream, repository, and dependency-injection conventions while requiring a credential-safe HTTPS or loopback transport for pipeline requests; loopback HTTP bypasses configured/environment proxies so it remains direct.
- Complete the continuation sequence observed during a multi-page running-run list before writing stdout, subject to fixed page/run/response-size safety ceilings, and reject malformed, ambiguous, blank, or cyclic continuation responses.
- Drive implementation through client, CLI, real-wiring, and documentation tests before running full project gates and multi-perspective review.

**Non-Goals:**

- Polling, waiting for completion, retries beyond the existing HTTP client's behavior, or watch/stream output.
- Queued/not-started, postponed, or cancelling-run listing; `pipeline list` means the Build API's exact `inProgress` status. `pipeline get` can still inspect a run in any status.
- Pipeline definition, branch, repository, requester, time-range, result, or arbitrary status filters.
- Stage, job, task, timeline, log, artifact, approval, environment, or deployment-resource details.
- Classic Release releases/deployments or the separate Release API host/scope.
- Queueing, cancelling, retrying, approving, or otherwise mutating pipelines and deployments.
- Repository-local context export or changes to existing work-item, pull-request, wiki, configuration, or credential behavior. The new transport validation applies only to pipeline requests.

## Decisions

### 1. Add a singular pipeline namespace with list and get actions

Register these read-only commands under the existing `ado` namespace:

`adomi ado pipeline list [--profile <profile-name>] [--global]`

`adomi ado pipeline get <run-id> [--profile <profile-name>] [--global]`

`list` deliberately requests only `inProgress` Build API runs in the configured project, including YAML and classic Build pipelines; it does not silently include other non-terminal statuses. It traverses the continuation sequence returned during that invocation but does not promise a transactionally complete point-in-time snapshot because runs can start, finish, or move between pages. Classic Release deployments remain excluded because they use a separate API surface. `get` requires a decimal Build API run ID from `1` through `2147483647`. Parse it with an explicit signed-32-bit bound before converting to Go `int`, making behavior independent of machine word size; zero, negatives, overflow, and non-decimal input fail before repository, config, keyring, or HTTP access. Both parsers also reject missing/value-less flags, unknown arguments, and repeated `--profile` or `--global` at that early-validation boundary, following the strict wiki parser pattern (`internal/cli/ado.go:946-996`). Help is handled before dependencies, matching the current command construction (`internal/cli/root.go:154-166`).

Both commands reuse the existing profile/client creation flow in `newADOMaintenanceClient` without changing its behavior (`internal/cli/ado.go:480-518`). Consequently, they run from a Git repository even with `--global`, because `resolveLocations` currently resolves the repository before the home/config paths (`internal/cli/ado.go:832-845`). This keeps the first slice consistent with agent workflows and avoids a configuration-semantics change unrelated to pipeline status.

Alternative considered: add one overloaded `pipeline status [run-id]` command. Rejected because omission of the ID would change the response cardinality and make help, validation, and automation less explicit.

Alternative considered: make `--global` work outside a repository for these commands. Rejected for this change because it would introduce a new location-resolution path rather than reusing the established network command flow.

### 2. Model Build API runs behind a narrow read interface

Add pipeline-run models and a `PipelineRunReader` interface in a focused `internal/ado/pipeline.go`, with `ListInProgressPipelineRuns(context.Context)` and `GetPipelineRun(context.Context, int)`. The interface contract returns only fully validated and normalized pipeline-run models or an error. Azure DevOps wire-shape validation, status/result consistency, optional-string normalization, timestamp normalization, identity checks, pagination validation, and safety ceilings belong exclusively to the `internal/ado` implementation. Embed that interface in `internal/cli.ADOClient`, wire the production `*ado.Client` through the existing factory, and extend the shared test fake (`internal/cli/root.go:35-64`, `internal/cli/ado_test.go:3052-3112`). No new package or third-party dependency is needed (`go.mod:1-18`).

The CLI trusts the `PipelineRunReader` contract and only maps validated models to the stable JSON DTO/envelope, marshals the result, and enforces output-stream behavior. It does not duplicate or reinterpret Build response validation. CLI fake tests therefore use already-normalized models for successful projection and return dependency errors to represent client-side validation failures. Repository, configuration, keyring, HTTP-client factory, ADO-client factory, and reader errors continue through the existing CLI/main error path unchanged; the CLI does not attempt to sanitize arbitrary dependency text.

The Build API model contains only fields needed by the output contract: run ID, build number, definition ID/name, status, result, source branch/version, queue/start/finish times, and `_links.web.href`. The Build response's REST `url` and other unrelated fields are ignored rather than stored or projected. Client validation requires run and definition IDs in the positive signed-int32 range, non-blank definition name/build number/status, and an exact response/request ID match for `get`. Result normalization trims surrounding whitespace and treats missing, null, empty, whitespace-only, or exact `none` as unavailable. Exact status `completed` requires an available non-`none` result; any other status requires the result to be unavailable. A non-completed response with an available result and a completed response without one are rejected as inconsistent shapes. Unknown non-blank statuses remain valid with an unavailable result, and unknown non-blank result values remain valid for completed runs, preserving forward compatibility without returning contradictory status data. For `sourceBranch`, `sourceVersion`, and `_links.web.href`, missing, explicit null, empty, or whitespace-only input becomes unavailable; other values have surrounding whitespace removed before projection.

Optional source fields, timestamps, and web links remain nullable. Optional source/link strings never project as empty or whitespace-only JSON strings: missing, null, empty, and whitespace-only inputs become null, while non-blank inputs are trimmed at both ends. Date-time fields decode through `time.Time`; malformed dates fail strict JSON decoding instead of being forwarded as apparently valid status data. Each available queue/start/finish time is normalized to UTC and formatted with `time.RFC3339Nano`: whole seconds use the `YYYY-MM-DDTHH:MM:SSZ` form, while non-zero fractional seconds retain nanosecond precision with insignificant trailing zeros removed. Unavailable timestamps remain JSON null. These are the data-shape assumptions: Azure DevOps returns Build-shaped JSON, definition identity is present, only exact `completed` status carries an available terminal result, and documented date-time fields are RFC3339-compatible. Violating an assumption returns an error and leaves stdout empty.

Alternative considered: expose the complete Azure DevOps Build object unchanged. Rejected because it is large, unstable for consumers, and includes unrelated queue/controller/repository details.

### 3. Use the Build list/get endpoints with bodyless strict JSON reads

`ListInProgressPipelineRuns` calls `{base}/{project}/_apis/build/builds` with `statusFilter=inProgress`, `queryOrder=queueTimeDescending`, the configured `api-version`, and a `continuationToken` on subsequent pages. It preserves the order in which the service returns runs across pages, requires the top-level `value` property to be present, normalizes an explicit null `value` to an empty non-nil slice, and accepts an empty array as an empty page. An omitted `value` is an unexpected response shape and fails instead of being reported as no running pipelines. The client rejects non-`inProgress` items and duplicate run IDs and follows the `X-MS-ContinuationToken` sequence observed during the invocation. An absent continuation header ends pagination. Exactly one non-blank header value continues pagination using that opaque value unchanged; tokens are never parsed, ordered, or compared lexically. Empty or whitespace-only values, multiple header values, and any token already observed during the invocation are ambiguous or cyclic and fail before another request. This follows the cycle-guard principle in the existing paged PR iteration client (`internal/ado/client.go:334-360`) without assuming that opaque tokens have an advancement order.

Pagination is bounded by fixed implementation constants: at most 1,000 response pages, including the initial page, and at most 100,000 accumulated validated runs. Each page's `value` array is stream-decoded and the remaining run allowance is checked before decoding an excess element, preventing an oversized array from allocating past the run ceiling before rejection. Exactly-at-limit results may succeed only when the final allowed page has no continuation header and the accumulated run count does not exceed the run ceiling. If the 1,000th page still advertises another token, or appending a page would exceed 100,000 runs, the operation fails atomically without requesting an over-limit page or writing stdout. These are defensive safety ceilings rather than user-configurable product filters; caller cancellation and the shared HTTP client's 60-second per-request timeout remain effective. An empty page with a new token is valid within these ceilings; an empty final response becomes `{"runs":[]}`. The client does not restart, poll, or reconcile pages when project state changes during traversal, so the accumulated result is a best-effort one-shot view rather than a transactional snapshot.

`GetPipelineRun` calls `{base}/{project}/_apis/build/builds/{run-id}` with the configured `api-version` and validates the returned identity/shape. Before constructing or sending either authenticated pipeline request, the client validates the configured base URL transport. HTTPS is accepted. HTTP is accepted only when `URL.Hostname()` is exactly `localhost` case-insensitively or parses as an IPv4/IPv6 loopback address; ports are allowed, but other hostnames, non-loopback IPs, and all other schemes fail before a request or `Authorization` header is created. No DNS lookup is used to classify a hostname as loopback. For loopback HTTP, each list/get operation clones one supported shared transport, clears its proxy function, reuses it for the operation's full request sequence, and closes its idle connections afterward. This prevents an explicit profile proxy or environment proxy from receiving the Basic PAT without losing pagination keep-alive reuse or changing proxy behavior for HTTPS and existing non-pipeline commands. This capability-specific guard keeps `httptest` and local development viable without changing transport behavior for existing Adomi operations; non-TLS remote/on-premises profiles cannot use the new pipeline commands.

Both operations issue bodyless GETs without `Content-Type`, use Basic PAT authorization only after the transport check, reject redirects, suppress raw response bodies and redirect `Location` values from returned errors, and enforce exactly one JSON value. Each successful list-page or get response is limited to 8 MiB (`8 * 1024 * 1024` bytes). A declared `Content-Length` greater than the limit fails before decoding, and the body is also read through a limit of one extra byte so chunked, missing-length, or dishonest responses fail if they contain any byte beyond 8 MiB. A body of exactly 8 MiB remains eligible for decoding; size failures do not include body content in the returned error.

Pipeline HTTP errors contain only the operation, status code, and a safe action-oriented message; they never contain the PAT, an `Authorization` header or value, a response-body fragment including HTML, or a redirect target. Pipeline-specific request code may share a small bodyless-read option/helper with wiki reads, but it must not change the existing generic nil-body `doJSON` wire contract, unbounded success-response behavior, or status-error behavior that other operations and PR regression tests assert (`internal/ado/client.go:443-481`, `internal/ado/wiki_client.go:84-93`, `internal/ado/pullrequest_test.go:347-398`). The paged list reads response headers before closing each body and does not expose continuation tokens to CLI consumers.

Alternative considered: use `/_apis/pipelines/{pipelineId}/runs/{runId}`. Rejected because it requires a pipeline ID for lookup and does not provide the project-wide in-progress list required by this change, while the Build API supplies both operations and the needed overall fields.

Alternative considered: request stage/timeline data alongside a build. Rejected because it would change this from overall run inspection into execution/deployment diagnosis and require separate models and failure semantics.

### 4. Project Build responses into a stable compact JSON contract

Map each validated Build response to:

```json
{"id":123,"pipelineId":7,"pipelineName":"deploy-service","runNumber":"20260714.3","status":"inProgress","result":null,"sourceBranch":"refs/heads/main","sourceVersion":"abc123","queueTime":"2026-07-14T08:00:00Z","startTime":"2026-07-14T08:01:00Z","finishTime":null,"webUrl":"https://dev.azure.com/..."}
```

`pipeline get` writes one run object. `pipeline list` wraps the ordered objects as `{"runs":[...]}` so an empty result is explicit and valid JSON. All documented keys are present; unavailable result, source, timestamp, or web-link fields are JSON `null`, not omitted or synthesized. Optional source/link strings are trimmed when available and never emitted as empty strings. Available timestamps are projected as UTC `time.RFC3339Nano` strings with `Z`, so equivalent instants have one stable representation regardless of the offset or fractional precision returned by Azure DevOps. The output uses `writeJSONLine`, so success is exactly one compact JSON value followed by one newline (`internal/cli/ado.go:1500-1506`).

The runner obtains fully validated/normalized models from `PipelineRunReader`, projects them, and completes JSON marshaling before it writes success data. The production reader completes all requests, pagination, decoding, and validation before returning. Configuration, keyring, client construction, HTTP/status/redirect, decoding, pagination, reader validation, projection, and JSON encoding failures therefore return through the existing CLI error path with no success value on stdout (`cmd/adomi/main.go:10-14`). The real pipeline HTTP client constructs status/redirect/response errors that contain no PAT, `Authorization` value, raw response body, HTML fragment, or redirect `Location` value; because `main` prints the returned error unchanged, the same guarantee applies to production stderr for those client-produced errors. Arbitrary upstream dependency errors retain existing pass-through behavior and are outside this content-sanitization guarantee.

Alternative considered: human-readable tables by default with optional `--json`. Rejected because the primary consumer is agent/script inspection and the user approved compact JSON for this version.

### 5. Keep the capability discoverable and explicitly read-only

Add both commands, their one-shot overall-run semantics, `vso.build` PAT requirement, HTTPS-or-loopback transport requirement, and exclusions to the generated Adomi skill and its required-content assertions (`internal/cli/agent.go:110-224`, `internal/cli/agent_test.go:405-464`). Add concise examples to `README.md` and the command inventory in `docs/adomi_azure_devops_handover.md`. Cobra namespace/action help must describe the exact status filter, run-ID range `1..2147483647`, profile/global and repository behavior, transport requirement, JSON schema, nullable result semantics, and absence of polling/detail/mutation.

No command calls queue, update, cancel, retry, release, timeline, log, artifact, environment, or deployment endpoints. The PAT and derived `Authorization` value are never printed, embedded in success output, returned in errors, or written to stderr; the shared client continues to send the PAT only as Basic auth to URLs built from the configured base URL/project (`internal/ado/client.go:633-646`). Raw response bodies and redirect locations are likewise excluded from pipeline errors and stderr.

## Risks / Trade-offs

- **A run starts, finishes, or moves between pages while a multi-page list is being read** → Complete the continuation sequence observed during the invocation, preserve received order, reject duplicate IDs, and document that the result can omit concurrent changes because it is not a transaction, restart, reconciliation, or wait operation.
- **Azure DevOps returns an ambiguous, blank, or cyclic continuation token** → Accept only one non-blank opaque header value, track every observed token, and fail before looping or printing partial results.
- **Azure DevOps returns an unbounded sequence of unique pages or runs** → Stop at 1,000 response pages or 100,000 accumulated runs and fail atomically before issuing or exposing over-limit work.
- **One page encodes more runs than the remaining run allowance** → Stream-decode `value` and reject before decoding or allocating the first excess element.
- **Many allowed pages contain exceptionally large but valid projected strings** → The approved contract bounds each response, page count, and run count but deliberately has no aggregate-byte product limit; aggregate retained output can therefore still be large within those ceilings. Treat a stricter aggregate limit as a future product/spec decision rather than silently inventing one during implementation.
- **Top-level success is mistaken for deployment-stage evidence** → Name fields as overall run status/result and repeat stage/job/environment/classic Release exclusions in help, specs, README, and generated skill guidance.
- **The PAT lacks Build read permission** → Preserve the action-specific 401/403 diagnostic and document the `vso.build` requirement without exposing credential content.
- **An Azure DevOps error or redirect contains sensitive or attacker-controlled text** → Have the real pipeline HTTP client report only the operation, status code, and safe guidance; suppress response bodies, HTML, redirect locations, PATs, and authorization values from the returned error, which `main` then prints unchanged.
- **A profile uses an unencrypted remote Azure DevOps base URL** → Reject the pipeline operation before constructing or sending an authenticated request; allow HTTP only for exact localhost or parsed loopback IP endpoints.
- **A loopback HTTP profile also configures a remote proxy** → Create one proxy-bypassed transport per pipeline operation, reuse it across pagination, and close its idle connections afterward so authentication stays direct without leaking transports/connections.
- **Azure DevOps or a configured endpoint returns an oversized success body** → Reject declared or streamed bodies above 8 MiB per list page/get response before JSON projection, without including body content in diagnostics.
- **Azure DevOps returns a terminal result alongside a non-completed status or omits it for a completed run** → Reject the inconsistent shape rather than exposing contradictory status data; preserve unknown values only within the same status/result consistency rule.
- **On-prem Azure DevOps differs in supported Build API behavior** → Build paths from the configured collection base/project and use the profile API version; require HTTPS for remote/on-premises hosts and return transport/status/decode/shape errors rather than silently altering the output contract.
- **Adding `PipelineRunReader` breaks shared CLI fakes or existing operations** → Update the composite fake once, keep the interface read-only, and run existing `internal/ado`, `internal/cli`, and full-project tests after the interface/wiring chunk.

## Pre-Mortem

1. **`pipeline list` silently fails to traverse the observed page sequence, consumes unbounded resources, or is mistaken for a transactional snapshot.** Likely cause: ignoring a continuation token, accepting an ambiguous or cyclic token, omitting page/run ceilings, overwriting page results, or failing to document concurrent state changes. Mitigation: explicit continuation tests with multiple/empty/changing-state pages and page/run boundaries, opaque-token validation and cycle guards, duplicate-ID rejection, a real CLI wiring test that returns more than one page, and clear best-effort one-shot wording.
2. **Agents report a deployment as successful when only the overall build succeeded.** Likely cause: ambiguous names or undocumented exclusions. Mitigation: expose only `status`/`result` as overall run fields and state the absence of stage/job/environment/classic Release evidence in command help, generated skill guidance, README, and specs.
3. **A failed, oversized, or malformed response still consumes excessive memory or emits plausible JSON.** Likely cause: unbounded decoding, decoding an entire over-limit run array before checking the ceiling, streaming page output, or projecting before response validation. Mitigation: bound each successful response to 8 MiB, stream-decode `value` while enforcing the remaining run allowance before excess allocation, accumulate and validate the complete result within the separate page/run ceilings, require completed runs to have terminal results, marshal once, and call `writeJSONLine` only after every operation succeeds. Exceptionally large valid aggregate output within all approved ceilings remains the explicit residual trade-off above.
